How the program selects and runs a protocol

          
    
            
  1. Input. main() reads the protocol choice, frame count, sequence bits, windows and the frames/ACKs to lose.
    2. 
            
  2. Validation. validateConfig() enforces the window limits for the chosen protocol and rejects invalid setups.
    3. 
            
  3. Selection. The factory createProtocol() returns a StopAndWait, GoBackN or SelectiveRepeat object through an ARQProtocol* pointer.
    4. 
            
  4. Execution. The shared run() loop advances the clock, delivers channel events and calls the virtual hooks sendNext(), receiveFrame(), receiveAck() and onTimeout(). Virtual dispatch picks the protocol-specific behaviour.
    5. 
            
  5. Report. printSummary() prints transmissions, retransmissions, deliveries, discards, losses, timeouts, time and efficiency.
    6. 
          

          

            Channel model. One frame can be put on the link per time unit, frames and ACKs take 2 time units to cross, and the retransmission timer is 6 time units (longer than the 4-unit round trip). A frame or ACK selected for loss is dropped only on its first trip.
          

        


        

          
Questions

          

            a. Why can all three protocols share a common interface but need different protocol logic?
            
Every ARQ protocol does the same jobs: send frames, accept or reject them at the receiver, process acknowledgements and recover from timeouts. The abstract class ARQProtocol captures these jobs as virtual functions and implements the parts they all share: the clock, the lossy channel, timers, statistics and the main loop. The protocols differ only in the rules inside those jobs: window size, cumulative vs. individual ACKs, discarding vs. buffering out-of-order frames, and how much is resent after a timeout. Each subclass overrides the hooks with its own rules.

          

          

            b. Why must the sequence number space constrain the window size?
            
Sequence numbers wrap around modulo 2m. If the window is too large, the receiver cannot tell a retransmitted old frame from a new frame that carries the same number. For Go-Back-N, Ws = 2m would let a whole lost window of ACKs make the receiver accept duplicates, so Ws ≤ 2m − 1. For Selective Repeat the sender and receiver windows must not overlap after wrapping, so each must be at most half the space: W ≤ 2m−1.

          

          

            c. How does Selective Repeat reduce unnecessary retransmissions compared with Go-Back-N?
            
A Go-Back-N receiver discards every frame after a gap, so one loss forces the sender to resend the lost frame and every frame sent after it. A Selective Repeat receiver buffers correct out-of-order frames and acknowledges them individually. Each frame has its own timer, so only the frame that was actually lost (or whose ACK was lost) is resent. Run the same configuration in the Compare tab to see the difference in retransmissions.

          

          

            d. What changes are needed to add another ARQ protocol?
            
Write a new class that derives from ARQProtocol and implements sendNext(), receiveFrame(), receiveAck(), onTimeout(), finished() and name(). Then add a menu entry in main(), a case in createProtocol() and its window rule in validateConfig(). The channel, timers, main loop and report are reused unchanged.
